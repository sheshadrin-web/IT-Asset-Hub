You are working on the Miles Education IT Asset & Helpdesk Portal.

I want you to build Phase 1 of a new feature called:

USER PUSH / EMPLOYEE OS ACCOUNT PROVISIONING

This first phase is for macOS only.

IMPORTANT:
Do not redesign the full portal.
Do not break existing features.
Do not change current acknowledgement behavior.
Do not modify current Lock, Unlock, Restart, Wallpaper, Agent Update, Agent Registration, Agent Removal, Zoho integration, Asset Recovery, Windows agent behavior, or Ubuntu agent behavior unless a very small shared change is strictly required for this feature.

==================================================
BUSINESS GOAL
==================================================

IT prepares the laptop first.

For macOS:

1. IT installs macOS.
2. IT creates a permanent administrator account:
   miles-it-support
3. IT installs MilesAgent using admin privileges.
4. The agent runs as a system LaunchDaemon.
5. The laptop appears online in the Asset Portal.
6. IT assigns the laptop to an employee through the existing asset assignment flow.
7. The existing acknowledgement email is sent exactly as it works today.
8. Acknowledgement is independent from OS account provisioning.
9. IT then explicitly clicks:
   Push User to Device
10. The portal sends a new command to MilesAgent.
11. MilesAgent creates the assigned employee's macOS account.
12. The employee account must be a Standard User.
13. miles-it-support must remain Administrator and must never be modified.
14. The portal shows whether provisioning succeeded or failed.

Do NOT automatically acknowledge the asset when the employee logs into the Mac.

Do NOT require acknowledgement before User Push.

Do NOT automatically run User Push immediately after assignment.

User Push must be an explicit IT action.

==================================================
IDENTITY DESIGN
==================================================

Employee Code must be the canonical identity.

Do NOT use employee name as the unique identity because names may duplicate.

Example:

Employee Code:
MPE1340

Display Name:
employee's full name

Email:
employee official company email

macOS short username:
mpe1340

Rules:

- derive the local username from Employee Code
- convert Employee Code to lowercase
- validate allowed username characters
- reject invalid or malformed Employee Codes
- never derive the actual OS username from employee display name
- store Employee Code with the device-user provisioning record
- employee display name is only display metadata

PERMANENT PROTECTED IT ACCOUNT

miles-it-support

- demote it

- overwrite it
- treat it as the employee account
- include it in employee lifecycle cleanup

Also protect macOS system/service accounts such as:

and other normal macOS protected/system users

Create centralized protected-account validation.

Add the new functionality through the same architecture.

==================================================
NEW AGENT COMMAND
==================================================

Add a new command type:

provision_user

Example logical payload:

{
  "employee_code": "MPE1340",
  "display_name": "Employee Full Name",
  "email": "employee@mileseducation.com"
}

The agent should derive the macOS username itself from Employee Code.

Example:

MPE1340
->
mpe1340

Do not blindly trust a username sent by the frontend.

==================================================
SERVER-SIDE SECURITY
==================================================

The frontend must NOT be allowed to submit arbitrary employee data or arbitrary usernames.

When IT clicks:

Push User to Device

the backend should:

1. identify the asset
2. identify the current assigned employee
3. verify that assignment still exists
4. fetch employee data from the existing Users table
5. fetch Employee Code from the Users table
6. build the command server-side
7. send the command to the correct device agent

The backend should reject provisioning if:

- asset is unassigned
- employee is inactive
- Employee Code is missing
- agent is not installed
- asset is not macOS for Phase 1
- another provisioning command is already pending
- employee assignment changed while the request was being created

==================================================
macOS ACCOUNT CREATION
==================================================

Implement a dedicated macOS helper function for provisioning.

Do not put the entire implementation directly inside execute_command().

The employee account must be created as:

Short username:
lowercase Employee Code

Real/display name:
employee full name

Account type:
Standard User

Home directory:
normal macOS user home directory

Shell:
normal interactive shell

The employee account must NOT belong to the admin group.

Do not grant sudo/admin rights.

The provisioning logic must:

- verify the agent is running with root/system privileges
- determine a safe unused local UID
- never assume a fixed UID
- verify the username does not already exist
- verify there is no protected-account collision
- create the local account safely
- create/configure the home directory correctly
- return a meaningful status to the portal

If root/system privileges are unavailable, return:

Do not partially provision the user.

==================================================
IDEMPOTENCY
==================================================

Provision User must be safe to retry.

Scenario:

The account is created successfully but the portal misses the response due to a network issue.

The same command is retried.

The agent must not create a duplicate account.

If the expected local account already exists and matches the same Employee Code provisioning mapping:

return success such as:

User already provisioned

If the same username exists but belongs to a different identity:

return failed

Do not overwrite the existing account.

PASSWORD DESIGN
==================================================

Do not use the employee's corporate password.

Do not fetch or store Google, Zoho, Microsoft, Miles email, SSO, or any other employee password.

For Phase 1 use a secure temporary local login credential design.

Requirements:

- do not log plaintext password
- do not save plaintext password in command logs
- do not include password in inventory sync

If the existing architecture does not support secure one-time secret delivery, implement the provisioning framework safely and document the credential limitation instead of inventing a weak password scheme.
