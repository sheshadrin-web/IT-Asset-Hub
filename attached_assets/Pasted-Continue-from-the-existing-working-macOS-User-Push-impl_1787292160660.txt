==================================================
EXISTING BUSINESS MODEL — DO NOT CHANGE
==================================================

Permanent IT administrator account:

miles-it-support

This account is created by IT during OS preparation and must remain protected.

The normal lifecycle is:

OS installed
→ miles-it-support created as Administrator
→ Miles Agent installed with system/admin privileges
→ Asset appears online
→ IT assigns employee
→ Existing acknowledgement email is sent
→ IT explicitly clicks Push User to Device
→ Agent creates employee Standard User

Acknowledgement remains completely independent from User Push.

DO NOT:
- automatically acknowledge on OS login
- require acknowledgement before User Push
- automatically Push User immediately after assignment

==================================================
WINDOWS USER PUSH
==================================================

Implement a dedicated helper such as:

_win_provision_user(...)

Do not place the entire implementation inside execute_command().

Requirements:

1. Agent must be running elevated / Administrator / system context.

If not:

return:
requires_admin

2. Username:

MPE1340
→
mpe1340

3. Display/full name:

employee full name

4. Create a LOCAL Windows account.

Do not create:
- Microsoft account
- Entra ID account
- domain account

Phase 1 Windows User Push is local-account provisioning only.

5. Employee account type:

STANDARD USER

It must NOT be member of:

Administrators

6. Prefer native Windows account-management APIs / PowerShell / net user
according to existing project conventions.

7. Create home/profile normally through Windows account lifecycle.

Do not manually create a fake profile directory.

Windows should create the user profile naturally on first login.

8. Verify after creation:

- local user exists
- account enabled
- username matches
- employee is NOT Administrator
- miles-it-support remains Administrator

9. Store the Employee Code marker/mapping using the existing provisioning database mapping.

If a safe local marker is useful, implement one without exposing secrets.

==================================================
WINDOWS TEMPORARY PASSWORD
==================================================

Reuse the existing secure one-time credential architecture developed for macOS.

Do NOT create a new password transport system.

Requirements:

- password generated locally by the agent
- cryptographically secure
- never logged
- never put in device command payload
- never put in device command result
- never put in audit trail
- encrypted before backend storage
- one-time reveal through existing provisioning credential flow
- same expiry behavior as macOS

When invoking Windows account-creation tools, avoid exposing the password in:

- command-line arguments
- process listings
- PowerShell history
- logs

Prefer stdin / secure process invocation where technically possible.

If Windows APIs require different handling, implement the safest available approach and document the limitation.
